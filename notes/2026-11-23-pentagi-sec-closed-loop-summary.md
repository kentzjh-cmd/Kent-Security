## 一句话结论

以 CVE 情报为输入的「PoC 无害化 → 沙箱执行 → WAF 变异验证 → 影子规则 → 审批阻断」双向闭环可以零人工干预跑通；其可信度来自把安全编排引擎（PentAGI）与通用 coding agent 的短板分别用外部控制面和工具子 agent 补齐，而不是指望任何一方的内置能力。在甲方工程落地中，进一步结合自身代码/版本/配置白盒上下文与攻击链模块化拆解，可以用最小的 token 成本换取确定性的安全保证。

> 脱敏声明：本文只描述架构设计、工程方法论与经验教训，不包含任何实际渗透
> 过程、目标信息、内网拓扑、IP/域名、凭据或漏洞利用细节。所有结论均来自
> 源码实证与隔离靶场内的端到端实测。

## 一、项目定位

构建一套**受控的已知风险验证闭环**：以公开 CVE 情报为输入，经

```
PoC 无害化 → 沙箱执行 → WAF 变异验证 → 影子规则 → 审批阻断
```

的双向闭环，覆盖终端侧（EDR 利用链只读审计）与边界侧（云 WAF 虚拟补丁）两个验证单元。
项目性质为**防御验证**：所有验证动作均在自有隔离靶场内进行，生产侧写入一律走
影子模式先行、人工审批放行。

### 不变约束（贯穿全部代码与流程）

| 约束 | 内容 |
|---|---|
| 数据不出网 | LLM / embedding 全部本地推理；证据与报告禁止任何外部 API |
| 凭据零明文 | 只走环境变量 / 密钥托管；配置文件仅保留引用键名 |
| 默认拒绝 | 授权范围为空 = 拒绝一切；沙箱出网仅限白名单 + Canary |
| 写生产两阶段 | 防护规则一律 SHADOW_LOG → OBSERVED → APPROVED → BLOCKING |
| stdlib-only | Python 3.12 标准库实现全部自研代码，零第三方依赖 |
| 虚构 API 防护 | 对外部系统先内省确认字段再编码，禁止凭文档/猜测虚构 API |

## 二、架构设计

```
横切控制面（stdlib-only）
  scope 授权白名单 │ budget 限速预算 │ secrets 凭据托管
  evidence 签名证据链 │ rollout 两阶段下发状态机
        │ 控制
        ▼
L1 情报摄入 → L2 可达性推演(图谱拓扑预置) → L3 双验证单元(终端+WAF)
  → L4 技能自演化(带双侧指标门禁与止损线) → L5 沙箱执行与复测

数据通道（实测确立）:
  通道 A  图数据库/图谱 —— 拓扑预置（英文结构化摄取协议）
  通道 B  向量库 + 知识文档/任务描述 —— 漏洞知识主通道
  通道 C  GraphQL 任务执行 —— 仅使用内省实证字段
```

### 调度层

运行时调度采用外部 coding agent 作为入口，安全逻辑**单一实现**保留在
stdlib CLI 控制面，扩展层（TS 薄层）不复制任何控制逻辑：

- `scope-gate` 门禁：bash 命令目标逐个过 CLI 授权检查，fail-closed；
  破坏性命令人工确认（headless 模式直接拦截）。
- 16 个调度工具统一转调 stdlib CLI（scope / budget / evidence / skill /
  flow / graphiti / rollout / recon 七组子命令）。
- flow 创建必须先干跑再提交；预算预检为提交前置条件。

## 四、关键技术结论与经验教训（已脱敏）

### 4.1 模型与图谱通道

- **小模型（3B 级）实体抽取是概率性的**：图谱边签名校验会丢弃非法边，
  连带触发「无边实体清理」，表现为静默 0 落库。误导因素是日志白名单过滤
  掩盖了内部 WARNING——**真相必须去容器内文件日志找**。
- 修复路径：改用**英文结构化输入协议**（一行一事实）+ 源码补丁（compose
  override 只读挂载，不重建镜像），端到端验证通过。
- 决策：漏洞数据主通道走向量库；图谱只做拓扑预置。GPU 显存不足以承载
  更大模型时，接受小模型能力边界并在通道设计上绕开。
- Maven 仓库的 APOC 包是残包，必须用 GitHub release 的 `-core.jar`。

### 4.2 外部引擎白盒结论

- **引擎无任何内置范围限制**（源码全量检索证实 + 422 反证）：范围控制必须
  由自研控制面 + 沙箱网络层兜底，不能指望上游执行。
- **提示词可经 DB 覆盖**（编译内嵌仅是默认值）：无需改镜像即可改写 agent
  语义，且重启持久；覆盖生效与否要看 `userDefined` 而非 `default`。
- 沙箱安全基线上游已达标（CapDrop: ALL + 显式能力白名单），优于自拟预设。
- 工具镜像内含全量渗透工具：约束只能靠提示词 + 出网白名单，**不能靠删文件**。
- 认证/REST/GraphQL 签名一律**内省实证**，多次踩坑证明「凭文档猜字段」必然 422。

### 4.3 调度与工程流程

- **长对话不适合做数据采集**：大模型思考输出撞上限导致系统性截断；
  采集必须下沉到工具子 agent，调度层只做解读与组装。
- 引擎重启不恢复运行中的任务；恢复通道是显式 input 动作，
  该动作已封装为调度工具使其可自主执行。
- 隔离网络内容器 IP 会漂移：入口地址必须**运行时解析**，报告以实测为准。
- 侦察链加 nuclei phase 的要点：模板离线固化进构建上下文（构建不依赖网络运气）、
  限速、禁外部 OOB 回连（数据不出网约束的落实）。
- WAF 判定信号以防护事件的负载与规则 ID 字段为主；拦截页存在「标准 403 型」
  与「200 变体型」两种形态，**判定必须看 body 标记**，不能只看状态码。

### 4.4 端到端验证结论（方法论层面）

- 全流程（侦察 → 任务书 → 干跑 → 提交 → 监督 → 收割 → 证据链）可零人工干预
  走通，全程在授权范围与请求预算内，0 违规。
- 已知模板类攻击（nuclei high/critical）被 WAF 全拦截，与人工验证结论一致；
  阳性对照模板正常命中，链路可信。
- 防护有效性评估应区分三类结果：确认绕过 / 部分穿越（穿越 WAF 但破坏后端
  词法等双刃行为）/ 确认拦截，并以无害化证据支撑每一类判定。

## 七、PentAGI（安全编排引擎）与通用 Coding Agent 的实际区别

项目同时使用了**专用安全编排引擎**（PentAGI）与**通用 coding agent**（作为调度
主脑），二者在闭环中承担完全不同的角色。以下区别全部来自源码实证与端到端实测。

### 7.1 维度对照

| 维度 | PentAGI（安全编排引擎） | 通用 Coding Agent（调度主脑） |
|---|---|---|
| 定位 | 面向渗透测试任务的**编排执行引擎**：flow 即子任务 DAG，agent 在沙箱内自主推进子任务 | 通用任务的**调度与决策主脑**：解读、组装、审批、驱动 CLI 工具链 |
| 执行环境 | 自带 Docker 沙箱 worker（CapDrop: ALL + 显式能力白名单），工具镜像内含全量渗透工具 | 无沙箱，直接访问宿主文件系统与 shell，靠 skill/工具协议扩展 |
| 范围控制 | **无任何内置 scope**（源码全量检索 + 422 反证实证），可被诱导探测任意地址 | 可在每条命令执行前过授权门禁（fail-closed），破坏性动作可要求人工确认 |
| 交互模型 | 异步任务：创建 → 轮询 → 收割；中途只能显式 input 注入，不支持实时对话 | 实时对话与审批闭环；调度循环每一步都可插人工确认 |
| 状态与恢复 | flow 状态存 DB；**重启不恢复 running 任务**，恢复依赖显式 input 动作点火 | 会话上下文 + skill 文件持久化；调度状态由证据链与 CLI 台账承载 |
| 接口形态 | REST / GraphQL，字段必须内省实证（凭文档猜必 422） | 文件系统 + bash + skill 协议，扩展成本低 |
| 长任务 | 擅长：长时受控执行、工具调用、产物收割 | 短板：长对话数据采集会撞输出上限被系统性截断 |
| 决策能力 | 弱：执行侧 LLM 只做子任务推进，无全局调度视野；易停滞（实测出现过 agent 循环空转，需外部输入点火） | 强：负责侦察 digest 解读（measured/inferred 分级）、任务书组装、预算与范围裁决 |

### 7.2 实际分工结论

- **Coding agent 只当主脑，不当执行器**。安全逻辑单一权威实现在 stdlib CLI
  控制面，agent 侧扩展只做薄封装、不复制任何控制逻辑；agent 不直接跑渗透
  工具——数据采集一律下沉到沙箱内的工具子 agent。
- **PentAGI 只当沙箱执行器，不当决策者**。它的价值是隔离执行环境与子任务
  DAG 编排；范围、预算、证据、审批、两阶段下发全部由外部控制面承担，
  因为源码实证它不提供这些能力。
- **数据采集必须下沉**：调度主脑的长对话侦察不可行（输出截断），正确形态是
  "侦察 worker 在沙箱内采集 → 主脑解读 → 任务书注入 → 干跑 → 提交"。
- **恢复通道要工具化**：引擎重启后的任务恢复动作应封装为调度工具，使调度
  循环可自主执行，不依赖人工 curl。
- **授权语义靠提示词补齐不可靠，必须双层**：提示词覆盖（默认拒绝 + 范围外
  硬停）是软约束，网络层隔离与门禁 gate 才是硬约束；两层都要有。

### 7.3 一句话总结

PentAGI 解决"**在哪里安全地执行**"，通用 coding agent 解决"**由谁谨慎地决定
执行什么**"；闭环的可信度来自把两者的短板分别用外部控制面与工具子 agent
补齐，而不是指望任何一方的内置能力。

## 八、方法论延伸：甲方白盒视角与攻击链模块化验证

### 8.1 甲方白盒上下文下的确定性安全验证

结合本项目实践进一步看，**甲方企业在 AI 赋能安全上最大的结构性优势，并不在于让 AI 模仿外部攻击者去做黑盒盲测，而在于甲方天然掌握完整的白盒上下文——源码、组件版本信息与真实配置信息**。

- **从「黑盒概率探索」转向「白盒确定性验证」**：传统或外部视角的 AI 渗透测试，大量 token 与请求预算消耗在资产探测、指纹猜测和试探性扫描上；而甲方拥有代码、版本（SBOM/依赖清单）与运行配置，可以先通过确定性比对锁定高概率/已知漏洞与配置缺陷，再让 AI 聚焦于**白盒渗透测试与已知漏洞的利用验证**（可达性分析 + 无害化 PoC 验证）。
- **以最小 token 成本换取确定性的安全保证**：
  1. **收敛推理空间**：用确定的代码路径、精确版本号和真实配置直接替代开放式发散试探，显著降低长上下文探索带来的 token 消耗与截断风险（与 4.3 节「长对话不适合做盲目采集」相互印证）。
  2. **结果可实证、可闭环**：已知漏洞的利用验证产出的不是「可能存在」的概率性告警，而是可复现的可达性证明或 WAF/终端拦截实证——用**确定性的漏洞**，以**最低的推理与执行成本**，换取**确定性的安全保证**。

### 8.2 漏洞验证的模块化拆解与攻击链串联裁决

与前文架构中的 `L2 可达性推演` 和 `L3 双验证单元（终端 + WAF）` 相呼应，在具体验证逻辑上，不应把「一个漏洞能不能打穿」当作单一黑盒任务让 agent 一竿子捅到底，而应把完整流程**拆分为映射到真实攻击链关键步骤的独立子模块**，分别实证后再做串联裁决：

```
[1. 边界绕过模块]         [2. 白盒可达性模块]        [3. 终端对抗模块]
WAF 是否存在绕过机制？ ──▶ 当前代码/版本/配置下 ──▶ 是否可关闭或噤声
(拦截 / 部分穿越 / 绕过)    漏洞是否真实可触发？      EDR / Defender？
        │                         │                         │
        └─────────────────────────┴─────────────────────────┘
                                  ▼
                    [攻击链串联与风险裁决]
          • 关键环节全成立 ──▶ 确认真实可利用攻击链（高优阻断/修复）
          • 任一关键环节不成立 ──▶ 攻击链断裂（不构成重大威胁，可降级归档）
```

这种「**分步模块化验证 + 攻击链串联**」的设计带来三个直接收益：

1. **对应真实纵深防御，避免单点高危误判**：生产环境的风险取决于攻击链能否走通，而不是孤立 CVE 评分。例如，某漏洞即便在代码层成立，但如果边界侧验证确认 **WAF 无可用绕过机制**，或终端侧（只读非破坏性推演）确认 **EDR / Defender 无法被关闭或噤声且必然触发阻断告警**，就可以得出「**该攻击链不成立，不构成重大威胁**」的确定性结论，把有限的应急与修复资源集中到真正能串成链的缺口上。
2. **模块边界清晰，支持按需短路与低成本并发**：每个子模块只回答一个确定性问题（如 WAF 变异绕过、白盒配置可达性、终端防御绕过/噤声权限），上下文短小、token 消耗可控；前序关键节点一旦确认阻断，还可直接短路后续昂贵验证，进一步压低整体成本。
3. **沉淀可审计的排除依据**：对于被判定为「不构成重大威胁」的漏洞，系统保留的是各子模块的实证证据链（而非主观忽略），后续一旦环境配置、WAF 规则或终端策略发生变更，只需重跑对应受损模块即可完成回归复核。

## 已被推翻的判断

- **「引擎文档里的字段可以直接用」**——GraphQL `scopeWhitelist`、`typeArg`、
  `valid`、`flows(limit:N)` 等多个字段/签名凭文档使用全部 422，最终全部以内省
  实证结果为准。
- **「从引擎返回值判断图谱落库成功」**——边校验在返回前已完成丢弃，返回值
  与日志均无法反映真相，必须查数据库与容器内文件日志。
- **「提示词改好 = 范围控制到位」**——提示词是软约束，实测侧仍需网络层隔离
  与命令级门禁作为硬约束。
